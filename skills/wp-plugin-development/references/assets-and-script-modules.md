# Assets: scripts, styles, script modules, editor assets

Use this file when a plugin loads JavaScript or CSS anywhere (frontend, wp-admin, block editor).

## Classic scripts and styles

```php
add_action( 'wp_enqueue_scripts', function () {
	if ( ! is_singular( 'acme_review' ) ) {
		return; // load only where needed
	}
	$asset = include ACME_REVIEWS_DIR . 'build/frontend.asset.php'; // generated by @wordpress/scripts

	wp_enqueue_script(
		'acme-reviews-frontend',
		ACME_REVIEWS_URL . 'build/frontend.js',
		$asset['dependencies'],
		$asset['version'],
		array( 'in_footer' => true, 'strategy' => 'defer' )
	);
	wp_set_script_translations( 'acme-reviews-frontend', 'acme-reviews' );

	wp_enqueue_style( 'acme-reviews-frontend', ACME_REVIEWS_URL . 'build/frontend.css', array(), $asset['version'] );
	wp_style_add_data( 'acme-reviews-frontend', 'rtl', 'replace' ); // if the build emits frontend-rtl.css
} );
```

Guardrails:

- Hooks: `wp_enqueue_scripts` (frontend), `admin_enqueue_scripts` (admin, check `$hook_suffix`), `login_enqueue_scripts`. Never print `<script>`/`<link>` tags directly.
- Load conditionally (your admin screen, `has_block()`, `is_singular()`, shortcode present). Loading assets on every page is the most common plugin performance complaint.
- Version every asset (the `.asset.php` hash or the plugin version) so caches bust on release.
- Use the dependency array instead of bundling copies of libraries core ships (`jquery`, `wp-element`, `wp-components`, `wp-api-fetch`, `wp-i18n`...). `@wordpress/scripts` externalizes `@wordpress/*` packages to those handles automatically.
- Loading strategies (WP 6.3+): `'strategy' => 'defer'` or `'async'` in the args array. WordPress downgrades the strategy if a dependent script requires it.
- Pass data to scripts with `wp_add_inline_script( $handle, 'const acmeReviews = ' . wp_json_encode( $data ) . ';', 'before' )` or `wp_localize_script()`. Never put secrets in this data.
- No remote JS/CSS (CDNs) for code the plugin could ship locally; WordPress.org guideline 8 disallows executing remote code, and loading third-party assets is a privacy disclosure.
- Provide RTL styles for admin and frontend CSS when layout is direction-sensitive (`@wordpress/scripts` can generate `*-rtl.css` with rtlcss), and prefer logical CSS properties (`margin-inline-start`).

## Script modules (ES modules)

WP 6.5+ has a separate API for native ES modules (used by the Interactivity API):

```php
wp_register_script_module( '@acme-reviews/view', ACME_REVIEWS_URL . 'build/view.js', array( '@wordpress/interactivity' ), ACME_REVIEWS_VERSION );
wp_enqueue_script_module( '@acme-reviews/view' );
```

- Modules have their own IDs and dependency graph; they can't be enqueued with `wp_enqueue_script()` and vice versa.
- Pass server data to a module with the `script_module_data_{$module_id}` filter (WP 6.7+) and read it from the `wp-script-module-data-{$module_id}` JSON script tag.
- WP 7.0 allows classic scripts to declare dependencies on script modules (Trac #61500); check the 7.0 dev notes for the exact argument before using it, and keep a fallback if `Requires at least` is below 7.0.
- Blocks declare modules in `block.json` with `viewScriptModule`; see `wp-block-development` and `wp-interactivity-api`.

## Block editor assets

The editor content area is an iframe (always for the post editor from WP 7.1; in 7.0 whenever all blocks use Block API v3). Assets enqueued in the parent document don't reach the content.

| Asset | Where it goes |
| --- | --- |
| Editor UI (sidebars, plugins, panels) | `enqueue_block_editor_assets` |
| Content styles needed in both frontend and editor canvas | `enqueue_block_assets` (runs for the iframe too), or `block.json` `style` |
| Editor-only block styles | `block.json` `editorStyle` |
| Block scripts | `block.json` `editorScript`, `script`, `viewScript`, `viewScriptModule` |

- Inside the editor, code that queries the content DOM must use the iframe's document (for example via `useRefEffect` or the block's ref), not the global `document`.
- Don't enqueue editor styles via `admin_enqueue_scripts`; they will not apply inside the iframe and can leak into the admin.

## Build tooling

- `@wordpress/scripts` (`wp-scripts build` / `start`) is the default toolchain: it handles JSX, externals, `.asset.php` files, and `block.json` discovery. WP 7.0's refactored `@wordpress/scripts` builds from directories and relies less on webpack; follow the version the repo pins.
- Commit sources; ship `build/` in the release zip (decide per repo whether `build/` is committed).
- Keep a readable (non-minified) source in the plugin or a public repo link: WordPress.org guideline 4 requires human-readable code.
